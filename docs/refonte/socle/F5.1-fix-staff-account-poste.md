# F5.1 — Fix StaffAccountService / StaffPersonnelData

## Cause exacte

L'erreur `Undefined property: App\Modules\Socle\Data\StaffPersonnelData::$poste` survient dans
`app/Modules/Socle/Services/StaffAccountService.php:44`.

Ligne en cause :
```php
if (! $roleName && $employee->poste
    && in_array($employee->poste, UserResource::rolesAutorises(), true)) {
    $roleName = $employee->poste;
}
```

**Pourquoi cela échoue** :
- `StaffPersonnelData` (définie dans `app/Modules/Socle/Data/StaffPersonnelData.php`) ne possède **pas** de propriété `$poste`.
- Ses propriétés publiques sont : `id`, `nom`, `prenom`, `telephone`, `statut`, `userId`, `role`, `niveauId`.
- Le `role` est bien fourni par l'implémentation `StaffPersonnelAdapter` via `$e->role?->name`.
- L'ancien code tentait d'utiliser `$employee->poste` en tant que fallback pour déterminer le rôle, mais ce champ n'est plus exposé dans le DTO suite aux frontières inter-modules par Contracts/DTO.

**Contexte** :
- `StaffAccountService` reçoit un `StaffPersonnelData` via le contrat `StaffPersonnelContract`.
- Le contrat est implémenté par `StaffPersonnelAdapter` (module RH) qui extrait les données du modèle `Employe`.
- Bien que `Employe` possède un champ `poste`, ce dernier n'est **pas** réinjecté dans `StaffPersonnelData` — seul `role` (le nom du rôle) et `niveauId` le sont.
- La tentative d'accéder à `$employee->poste` dans `StaffAccountService` provoque l'erreur 500 "Undefined property".

## Ancienne logique

Avant la refonte des frontières Socle ↔ RH, le code voulait utiliser la position du personnel comme rôle par défaut si aucun rôle n'était explicitement fourni :
1. Si `$data['role']` fourni → utiliser ce rôle
2. Sinon si `$employee->role` disponible → utiliser ce rôle
3. **Sinon si `$employee->poste` disponible et dans la liste des rôles autorisés** → utiliser `$employee->poste` comme rôle
4. Sinon → `$roleName` reste null, validation échoue avec "role must be in authorized roles"

Cette logique tierce (fallback `$employee->poste`) était pertinente à une époque où le DTO n'exposait pas encore le rôle explicitement, ou où le rôle était déduit de la position.

## Structure réelle de StaffPersonnelData

```php
readonly class StaffPersonnelData
{
    public function __construct(
        public int $id,
        public string $nom,
        public string $prenom,
        public ?string $telephone,
        public string $statut,
        public ?int $userId,
        public ?string $role,       // ← vient de $e->role?->name
        public ?int $niveauId       // ← vient de $e->niveau_id
    ) {}
}
```

Le champ `role` est déjà peuplé par l'adaptateur RH. Il n'y a pas besoin de fallback vers `poste`.

## Correction appliquée

**Fichier modifié** : `app/Modules/Socle/Services/StaffAccountService.php`

Suppression des lignes 44-46 (l'ancien fallback `$employee->poste`) :

**Avant** :
```php
$roleName = $data['role'] ?? $employee->role;
if (! $roleName && $employee->poste && in_array($employee->poste, UserResource::rolesAutorises(), true)) {
    $roleName = $employee->poste;
}
$niveauId = array_key_exists('niveau_id', $data) ? $data['niveau_id'] : $employee->niveauId;
```

**Après** :
```php
$roleName = $data['role'] ?? $employee->role;
$niveauId = array_key_exists('niveau_id', $data) ? $data['niveau_id'] : $employee->niveauId;
```

Le rôle provient désormais uniquement de :
1. `$data['role']` si fourni dans les données du formulaire
2. `$employee->role` (déjà présent dans le DTO, issu de `$e->role?->name`)

Aucun fallback vers `$employee->poste` n'est nécessaire ni attendu.

## Pourquoi poste n'a pas été réintroduit dans StaffPersonnelData

- **Frontière respectée** : Le Socle n'importe pas de Models RH directement (`Employe`, `PosteAdministratif`). Il utilise uniquement les Contrats publics (`StaffPersonnelContract`, `StaffPersonnelData`).
- **Responsabilité séparée** : Le rôle/utilisateur est géré par le service de création de compte (`StaffAccountService`) via le DTO qui ne transporte que les champs utiles à cette opération.
- **Pas de champ "poste" dans le besoin** : La création de compte n'a pas besoin du libellé de poste — elle a besoin du nom de rôle (`role`) pour assigner les autorisations via `AssignationRoleService`.
- **Éviter la duplication** : Ajouter `poste` au DTO uniquement pour faire disparaître cette exception serait une fuite de responsabilité vers le domaine RH, contre-indiquée par l'architecture actuelle.

## Règle finale de détermination du rôle

Lors de la création d'un compte personnel via `StaffAccountService::create()` :

1. **Rôle explicite dans les données** : Si `$data['role']` est fourni → utilisé tel quel (après validation via `Rule::in(UserResource::rolesAutorises())`).
2. **Rôle depuis le DTO** : Si aucun rôle dans les données, mais que `$employee->role` est présent → utilisé comme rôle par défaut.
3. **Aucun rôle** : Si `$roleName` reste null après les deux précédent cas → la validation `Rule::in(UserResource::rolesAutorises())` échouera proprement avec une `ValidationException` (message "role must be in authorized roles"), et non plus d'erreur 500 "Undefined property".

Aucune autre source (poste, département, etc.) n'est consultée pour déterminer le rôle.
