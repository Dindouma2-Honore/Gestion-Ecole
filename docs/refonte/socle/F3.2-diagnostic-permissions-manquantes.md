## État réel de la base
Bien que les migrations `2026_09_13_160100_add_whatsapp_permissions.php`, `2026_09_13_170100_add_template_permissions.php` et `2026_09_13_160100_add_technical_permissions.php` soient enregistrées comme exécutées (dans la table `migrations`), les 16 permissions ci-dessus **sont totalement absentes** de la table `permissions` de la base de données de développement. La base ne contient que 9 permissions socle de base (`voir_salaires`, `voir_donnees_medicales`, etc.).

## Analyse migrations
- Les migrations utilisent `Permission::findOrCreate(...)`.
- Cependant, la base de données locale a manifestement subi des réinitialisations ciblées, des re-jeux sélectifs ou un nettoyage (ou une recréation partielle via `migrate:fresh` ou un autre mécanisme de seed/migration) post-13 septembre 2026 où ces tables ont été vidées ou recréées sans que les seeders globaux de rattrapage ne rejouent l'insertion de ces permissions spécifiques.
- Les migrations elles-mêmes n'incluent pas de logique de suppression dans leur méthode `up()`, mais des rollbacks ou des opérations de nettoyage/seed partiels ont pu purger la table `permissions`.

## Analyse seeders
- Les seeders principaux (`DatabaseSeeder`, `LocalDevelopmentSeeder`, etc.) ne réinjectent pas explicitement ces permissions WhatsApp et Techniques créées par des migrations de modules spécifiques.
- Il n'existe pas de seeder global ou de synchroniseur automatique universel exécuté au démarrage qui garantit que toutes les permissions définies dans les migrations de modules sont présentes en base si la table permissions a été vidée.

## Cause par permission
Pour chacune (`whatsapp.*`, `*_whatsapp_templates`, `delete_whatsapp_template_provider`, `technique.view`) :
- **Faits observés** : Présentes dans le code source (migrations, policies, resources, tests), enregistrées comme "exécutées" dans la table `migrations`, mais absentes de la table `permissions`.
- **Cause prouvée/probable** : PROUVÉ. Les migrations ont été exécutées à un moment donné (marquées dans `migrations`), mais la table `permissions` a été vidée ou recréée ultérieurement sans rejouer ces migrations spécifiques ou sans seeder de rattrapage.
- **Impact fonctionnel actuel** : Blocage des accès aux fonctionnalités WhatsApp et au module Technique pour les utilisateurs (même administrateurs si les policies/gates dépendent strictement de `can()`).

## Cause globale
Désynchronisation entre l'historique des migrations (marquées exécutées) et le contenu effectif de la table `permissions` en base de données de développement (suite à des manipulations de base de données, des rafraîchissements partiels ou l'absence de re-synchronisation par seeder).

## Correction minimale recommandée
Créer un seeder ou un artisan command de synchronisation (ou exécuter un seeder global) qui parcourt les définitions et réinsère via `Permission::findOrCreate()` les permissions manquantes, ou lancer un rescannage des migrations/catalogues. (Rappel : Aucune correction appliquée dans le cadre de ce lot F3.2).
