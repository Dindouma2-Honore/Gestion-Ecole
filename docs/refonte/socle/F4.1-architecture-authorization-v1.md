# F4.1 — Architecture Authorization V1

## Statut
TERMINE

## État réel de V1
- **Contrats et Services** : `AuthorizationContract` implémenté par `AuthorizationService`. Supporte les décisions (`decide()`), vérifications granulaires (`canRead()`, `canWrite()`, `canExecute()`, `canPrint()`), l'octroi (`grant()`) et la consultation des grants (`grantsFor()`).
- **Sujets supportés (`AuthorizationSubjectType`)** : `USER`, `GROUP`, `RH_POSITION`.
- **Modèle de données** : Table `authorization_grants` avec `subject_type`, `subject_id`, `feature_id`, `can_read`, `can_write`, `can_execute`, `can_print`, `is_active`.
- **Résolution** : `AuthorizationPositionResolverContract` (avec une implémentation par défaut `NullAuthorizationPositionResolver`) résout les postes RH de l'utilisateur.
- **Tests** : Suite complète de tests unitaires/fonctionnels dans `AuthorizationServiceTest.php` couvrant les décisions granulaires, l'agrégation de groupe, l'agrégation de postes RH et le cumul de grants.

## Problèmes empêchant son utilisation réelle
1. **Absence de liaison avec l'authentification courante** : `AuthorizationService` prend un `int $userId` brut et ne s'intègre pas encore nativement avec les Gates de Laravel ou `Auth::user()`.
2. **Table de grants vide** : La table `authorization_grants` n'est pas alimentée par les seeders d'administration actuels (qui alimentent `habilitation_role_fonctionnalites`, `habilitation_groupe_fonctionnalites`, etc.).
3. **Absence de support natif pour `ROLE` / Spatie Role dans V1** : Les rôles Spatie ou Socle (`Role`) ne sont pas mappés comme un `AuthorizationSubjectType`, alors que les habilitations métiers existantes reposent massivement sur les rôles et groupes de l'application.
4. **Bypass Fondateur non codé dans V1** : Contrairement à `ModuleAccess` qui autorise globalement les rôles `Fondateur`, `Admin`, etc., `AuthorizationService` évalue strictement les grants enregistrés en base pour les sujets de l'utilisateur.

## Décision recommandée — SubjectType
### USER
- **Rôle architectural** : Permet l'attribution d'habilitations dérogatoires ou spécifiques à un compte utilisateur précis.
- **Justification** : Indispensable pour la gestion individuelle des permissions et le support des tests/cas particuliers.

### GROUP
- **Rôle architectural** : Permet l'attribution d'habilitations à un groupe d'utilisateurs (`Groupe`).
- **Justification** : Déjà opérationnel et testé dans `AuthorizationService`, s'aligne parfaitement avec les groupes administratifs et pédagogiques de l'application.

### RH_POSITION
- **Rôle architectural** : Permet d'attacher des droits aux postes occupés par le personnel dans l'organigramme RH.
- **Justification** : Fondamental pour lier les habilitations métiers aux fonctions administratives et enseignantes de l'établissement.

### ROLE
- **Rôle architectural** : Ne pas ajouter `ROLE` en tant que `SubjectType` natif de V1.
- **Justification** : `Role` (Spatie / Socle) reste géré par le système legacy (`HabilitationRoleFonctionnalite` et `hasRole()`). Ajouter `ROLE` à V1 créerait une duplication de modèles d'habilitation et complexifierait inutilement la coexistence avec Spatie. Les rôles existants peuvent être représentés par des `GROUP` ou des `RH_POSITION` dans l'architecture cible.

## Décision recommandée — Fondateur
- **Décision** : Le rôle Fondateur (et les super-admins) doit disposer d'un court-circuit (bypass) au niveau de l'évaluation ou de l'adaptateur V1, ou recevoir explicitement des grants globaux.
- **Justification** : Pour des raisons de sécurité, de maintenance et de cohérence avec `ModuleAccess`, un utilisateur Fondateur ne doit jamais se voir refuser une action V1 sous prétexte que `authorization_grants` est vide. Le bypass est la solution la plus robuste pendant la transition.

## Source de vérité pendant la transition
Tableau :
| Besoin | Source actuelle | Source cible | Transition |
|---|---|---|---|
| Nouvelles fonctionnalités | Catalogue + Habilitations dynamiques | Authorization V1 (`authorization_grants`) | Adoption progressive de V1 via adaptateur |
| Anciennes fonctionnalités | Spatie / HabilitationService | HabilitationService / Spatie | Maintien strict en l'état (legacy) |
| Rôles RH | Spatie Roles / `Employe` | Spatie Roles / RH modules | Maintien en l'état |
| Accès module | `ModuleAccess` (Spatie + `habilitations_roles`) | `ModuleAccess` / V1 | Maintien de `ModuleAccess` |
| Actions fines (Read/Write/Execute/Print) | Dispersées / Policies | Authorization V1 | Passage progressif vers V1 |

## Écriture des authorization_grants
Les `authorization_grants` doivent être alimentés soit via des seeders métiers ciblés, soit par une adaptation minimale des écrans existants (`ManageHabilitations` ou un nouvel écran dédié aux grants granulaires V1), sans écraser le système d'habilitation existant.

## UI d'administration cible minimale
Un widget ou une section onglet dans `ManageHabilitations` permettant d'affecter les 4 actions (Read, Write, Execute, Print) pour un sujet (`USER`, `GROUP`, `RH_POSITION`) sur une fonctionnalité du catalogue.

## Premier consommateur V1 recommandé
- **Fichier** : Un service ou une action non critique à fort besoin granulaire, par exemple l'évaluation des droits de consultation/impression de rapports dans le module Socle ou Pédagogie (ex: `ProgressionMonitoringService` ou un service de génération de documents).
- **Comportement actuel** : Vérification par rôle ou méthode legacy.
- **Comportement V1** : Appel de `$authorization->canRead($userId, $featureCode)` ou `canPrint()`.
- **Prérequis** : Alimentation d'un grant minimal dans `authorization_grants` pour la fonctionnalité cible.
- **Risque** : Aucun si un grant par défaut ou un test d'existence est prévu.

## Stratégie de coexistence
- Ne pas remplacer Spatie ni HabilitationService d'un seul coup.
- Utiliser `AuthorizationV1` en parallèle pour les nouveaux besoins d'actions granulaires (`READ`, `WRITE`, `EXECUTE`, `PRINT`), tandis que le legacy gère les rôles globaux et l'accès aux modules.

## Données initiales
Une table `authorization_grants` vide au démarrage est **totalement acceptable** pendant la transition, car le système legacy (`HabilitationService` / Spatie) continue de porter les habilitations courantes. Aucune migration automatique des 287 habilitations n'est requise.

## Modifications nécessaires pour rendre V1 opérationnelle
- **P0 indispensable** : Implémenter un adaptateur de façade (ex: `AuthorizationV1Gate` ou extension de `ModuleAccess`) permettant de consommer V1 proprement.
- **P1 transition** : Alimenter les grants de test/production initiaux pour les premiers consommateurs.
- **P2 futur** : Migration complète des policies vers les actions Read/Write/Execute/Print de V1.

## Ce qui NE doit PAS être fait maintenant
- Ne modifier aucun code.
- Ne pas supprimer Spatie.
- Ne pas modifier `AuthorizationService`.
- Ne pas écrire de grants.

## Plan F4 proposé
1. **F4.2** : Création d'un adaptateur de pont (Bridge) entre Auth/Gates de Laravel et `AuthorizationContract`.
2. **F4.3** : Migration d'un premier consommateur pilote vers V1 (ex: consultation de rapports Socle).
3. **F4.4** : Enrichissement des seeders de grants initiaux pour les rôles administratifs clés.

## Conclusion
- V1 PEUT ÊTRE ACTIVÉE PROGRESSIVEMENT : OUI
- ROLE DOIT ÊTRE AJOUTÉ À V1 : NON
- SPATIE PEUT ÊTRE SUPPRIMÉ : NON
