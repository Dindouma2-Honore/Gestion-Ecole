## 4. MATIERE — modèle

- `$fillable` = `nom, nature, categorie_matiere_id, code, coefficient_defaut, coefficient, description, actif` → **`type` n'est PAS fillable**, alors que 2 constantes et 2 scopes le utilisent.
- `booted()` : (a) auto-`code` unique (`Str::upper(Str::slug(nom))` borné à 20 + suffixe `_2`), (b) fallback `categorie_matiere_id ??= CategorieMatiere::code('NON_CLASSEE')`.
- `scopeMatieres()` = `where('type', 'matiere')`, `scopeDomaines()` = `where('type', 'domaine_activite')` : **jamais appelés nulle part** (0 occurrence hors définition) → dead code.
- Relations : `categorie()` (belongsTo), `programmes()` (hasMany), `offresPedagogiques()` (hasMany).

## 5. MATIERE — double discriminateur `type` vs `nature` (constat central)

Deux colonnes parallèles, **vocabulaires disjoints** :

| | valeurs attendues | qui écrit | qui lit |
| :--- | :--- | :--- | :--- |
| `type` | `matiere`, `domaine_activite` (`Matiere::TYPE_*`) | **personne en applicatif** (non fillable → écritures silencieusement ignorées) ; default DB | `scopeMatieres`/`scopeDomaines` (jamais appelés) + colonne Filament |
| `nature` | `matiere`, `domaine`, `activite` | `CatalogueMatiereService` (Filament) | `CatalogueMatiereService` (validation), colonne Filament |

Écritures **silencieusement perdues** (mass assignment, `$fillable` sans `type`) :

- `MatiereService::creer(..., string $type = TYPE_MATIERE)` → passe `'type' => $type` : ignoré.
- `ClassesPedagogiquesTest:70` et `SyntheseEmploiDuTempsTest:50` passent `'type' => Matiere::TYPE_DOMAINE_ACTIVITE` : ignorés (la matière reste `matiere`).
- Aucun champ `type` dans `MatiereResource::form()` → impossible de modifier `type` depuis l'UI ; la colonne affiche donc toujours le default.

Vocabulaire hétérogène supplémentaire : `type='domaine_activite'` (constantes) vs `nature='domaine'` (UI/validation) vs `ProgramDocumentAnalyzer` qui mappe `'maternelle' => 'domaine'` sur ses **propres** structures de programme (hors périmètre strict, mais même famille lexicale).

## 9. ORGANISATIONCYCLE — schéma, service, contexte

- Table `organisation_pedagogique_cycles` (`2026_09_28_020000`) : `id`, **`cycle_id` unique** (satellite de `cycles`), `mode`(20) nullable, timestamps. Aucune autre donnée (pas de code, nom, ordre).
- Init en migration : lecture brute `DB::table('cycles')->get(['id','code'])` + `match` **hardcodé** `'MAT','PRI' => 'classe'`, `'COL','LYC' => 'matiere'`, `default => null` + commentaire « New cycles require explicit configuration ».
- Model : `$fillable = ['cycle_id','mode']`, **aucune validation de modèle** (le `in:classe,matiere` n'existe que dans le service).
- `OrganisationCycleService` :
  - `autorise()` = `context()->canManage(Pages\Enseignements)` **&&** (`Fondateur` **ou** permission `gerer_parametrage`) ;
  - `enregistrer()` : Validator (`cycle_id` `distinct`, `mode` `in:classe,matiere`), cycle inconnu refusé via Contracts, `firstOrCreate` + `lockForUpdate` par cycle, **verrou de changement de mode** : si des `AffectationPedagogique` existent sur les classes du cycle (parcours niveaux → classes → années, tous via Contracts), le changement de mode est refusé, audit Socle systématique, transaction unique.

- Page `Enseignements` : action header « Organisation des cycles », Repeater non addable/deletable/reorderable, lecture `OrganisationCycle::where(...)->value('mode')` **dans une boucle → N+1** avant appel au service.
- `mode` peut rester `null` (cycle créé après l'init, ou `default => null`) : `modeClasse()` retourne alors `null`, ce qui alimente `AffectationPedagogiqueService` (hors périmètre strict, comportement à confirmer en P1.2).

## 10. ORGANISATIONCYCLE — duplique-t-il Scolarité ? **NON**

- `cycles` et `niveaux` appartiennent à **Scolarité** (migrations `app/Modules/Scolarite/...`, modèles `Scolarite\Models\Cycle|Niveau`, tables `cycles`/`niveaux`).
- Pédagogie ne lit ces tables **que via `AcademicStructureCatalogContract`** (`OrganisationPedagogiqueContext::cycles()/niveaux()`). La table Pédagogie ne stocke que `cycle_id` + `mode` : **aucune donnée dupliquée**, seule la clé étrangère logique est répétée (sans FK déclarée).
- Le `mode` est un **concept propre à Pédagogie** (principal/assistants par classe vs enseignants par matière) : il n'existe nulle part ailleurs → la satellite est la bonne forme.
- **Conclusion : `OrganisationCycle` = KEEP (satellite conforme), confirmé par cet audit.** À ne pas confondre avec `AffectationPedagogiqueResource::classeEstSecondaire()` (hors périmètre) : là, une règle de cycle **est** hardcodée et devrait passer par `modeClasse()`.

## 11. OFFREPEDAGOGIQUE — schéma et service

- Table (`2026_09_02_000003` + évolutions) : `matiere_id` FK `restrictOnDelete`, `niveau_id` (aucune FK), `filiere_id` nullable, `annee_scolaire_id` (aucune FK), `programme_id` FK `nullOnDelete`, `coefficient_matiere` (5,2 default 1), `volume_horaire` (7,2) null, `heures_hebdomadaires` (5,2) null, `actif`, + **`classe_id` nullable indexé** (`2026_09_12_000001`, réparé par `2026_09_28_010000`).
- Unicité : `offre_pedagogique_unique` (matière+niveau+filière+année) créée en 09_02, **supprimée** en `2026_09_12_000002` ; unicité restante = `offre_pedagogique_classe_unique` (**matière + classe + année**, MySQL : `classe_id NULL` distincts → **les offres de niveau ne sont pas couvertes par le DB**). La contrainte complète (année + niveau + classe + matière) n'existe **que dans le service**.
- Model : `$guarded = []`, casts `decimal:2` / `boolean`, relation `matiere()` — **pas de relations `niveau`/`classe`/`année`** (IDs scalaires, conforme P0.2).
- `OffrePedagogiqueService::enregistrer` : `context->assertWrite` (ModuleAccess + rôle + année ouverte à l'écriture), niveau accessible via Contracts, classe active rattachée au niveau, **contexte immuable** d'une offre existante (4 clés refusées → « créez une nouvelle offre »), unicité applicative, `lock(annee)` sur `organisation_pedagogique_verrous` + `lockForUpdate`, déduplication, `filiere_id` déduit de la classe, **audit Socle**.
- `effective(anneeId, classeId, matiereId)` : offre de classe **prioritaire** sur offre de niveau (`orderByRaw('classe_id IS NULL'`), null si `actif = false`.

## 12. OFFREPEDAGOGIQUE — rôle de pivot annuel : **OUI**

`(annee_scolaire_id, niveau_id, classe_id?, filiere_id, matiere_id)` est la clé de jonction annuelle utilisée par :

- `ProgrammeAccessService` : construit les accès enseignants/offres à partir des offres (`orderByRaw('classe_id IS NULL')`, fallback niveau) ;
- `AffectationPedagogiqueService` : stocke `offre_pedagogique_id`, et **refuse l'affectation si la matière est absente de l'offre** (« Ajoutez d'abord cette matière à l'offre pédagogique du niveau ou de la classe ») ;

## 16. Réponses aux questions du lot

1. **Matiere est-elle la source d'identité ?** OUI, pour le **catalogue** : `matieres` porte l'identité `id/nom/code` + catégorie ; l'identité **contextuelle** (année, niveau, classe, coefficient effectif) vit sur `offres_pedagogiques`. La matière n'a ni année ni niveau exploité (voir `niveau_id` mort).
2. **Les paramètres varient-ils par cycle/niveau sur Matiere ?** **NON** en logique applicative : aucun champ cycle, aucune règle par cycle. Seule trace : la colonne **`matieres.niveau_id` jamais lue ni écrite** (héritage `2026_09_07`, candidate à suppression ou à exploitation explicite).
3. **OrganisationCycle duplique-t-il Scolarité ?** **NON** (§10) : satellite `cycle_id + mode` sans données de cycle dupliquées, lecture de `cycles`/`niveaux` uniquement via `AcademicStructureCatalogContract`. **KEEP confirmé.**
4. **Les 3 cycles configurés diffèrent-ils des règles hardcodées ?** **OUI** (§14) : mode configuré en base (init hardcodée `MAT/PRI/COL/LYC` en migration) vs règles de cycle hardcodées ailleurs (`classeEstSecondaire()`, parsing `maternelle/primaire/secondaire`) — ces dernières sont hors périmètre et signalées.
5. **OffrePedagogique est-elle le pivot annuel ?** **OUI** (§12) : clé annuelle des programmes, affectations, accès enseignants et coefficients.
6. **Sources de coefficient/volume/année ?** Chaîne coefficient `Matiere.coefficient_defaut` → `AffectationPedagogique.coefficient` → **`OffrePedagogique.coefficient_matiere` (prioritaire)** ; volume/heures = offre seule ; année = offre (clé figée après création) + garde `assertWrite`.
7. **Nombre de SQL cross-module dans le périmètre ?** **Code applicatif : 0.** Migrations : **2 lectures/écritures brutes sur tables externes** — `DB::table('classes')` (Scolarité) dans `2026_09_12_000001` et `DB::table('cycles')` (Socle) dans `2026_09_28_020000` ; le reste des `DB::table` du périmètre vise des tables Pédagogie (`categories_matieres`, `matieres`, `offres_pedagogiques`, `affectations_pedagogiques`, `organisation_pedagogique_verrous`). Tests : 2 inserts bruts RH + Eloquent cross-module (Scolarité/Socle/RH) en fixtures.
