## OrganisationCycle

- Table : `organisation_pedagogique_cycles` — colonnes : `cycle_id` (unique), `mode`, timestamps.
- **Ne duplique pas** `Cycle`/`Niveau`/`Filière`/`Section` de Scolarité : c'est une table satellite qui porte un **paramètre pédagogique** (`mode` = `classe` | `matiere`, déduit du code cycle `MAT/PRI/COL/LYC`) référençant `cycle_id` en scalaire.
- Aucune relation Eloquent vers un Model Scolarité.
- **Verdict : ownership Pédagogie conforme.** KEEP.
- Observation : `organisation_pedagogique_verrous` (verrou par `annee_scolaire_id`) coexiste dans la même migration — logique d'organisation également pédagogique.

## Presence / Assiduité

`Presence` (`presences`) mélange deux responsabilités :

1. **Observation d'appel de séance (Pédagogie)** : `seance_id`, `eleve_id`, `statut`, `saisi_par` ; écrit par `PresenceService::faireAppel()` ; verrouillage lié à `Seance.appel_verrouille`.
2. **Suivi institutionnel d'assiduité (Assiduité)** : `heure_arrivee` (retard), `justifie`, `document_justificatif_id`, `motif` ; `PresenceService::justifierAbsence()` téléverse un justificatif via `DocumentServiceContract` (GED Socle).

Éléments confirmants :
- Le module **Assiduite existe** et possède déjà `JustificationAssiduite`, `AnomalieAssiduite`, `AssiduiteHistorique`, `AttendanceEngine` (qui **relit la table `presences` en SQL brut** comme source « appel_pedagogique »).
- Une migration historique a déjà retiré `statut_justification` / `justification_verifiee_par` de `presences` — le mélange a partiellement bougé mais pas complètement.

**Décision : SPLIT** (appel → Pédagogie ; justifications/retards/historique → Assiduité). Le split n'est **pas** effectué dans P0.2.

## AnomalieAppel

- Colonnes : `seance_id`, `detectee_le`, `notifiee`, `resolue`.
- Créée par `DetectionAbsenceService::detecterAnomalies()` = « appel non fait après X minutes de tolérance » sur une séance programmée → **anomalie pédagogique** (appel manquant), pas un incident institutionnel.
- Assiduité possède son propre `AnomalieAssiduite` (`anomalies_assiduite`) pour le suivi institutionnel — les deux ne se chevauchent pas.
- **Verdict : conforme.** KEEP.

## Devoir vs DevoirPedagogique

| | `Devoir` | `DevoirPedagogique` |

| Créée par | migration `2026_09_28_110300_creer_table_devoirs` | migration `2026_09_28_040000_versionner_programmes_progressions` |
| Clé métier | rattaché à une **séance** (`seance_id`) | rattaché à une **progression** (`progression_id`) + `classe_id`, `offre_pedagogique_id` |
| Écrit par | `ProgressionService` (saisie de progression) | `SessionProgressService` (enregistrement de séance) |
| Lu par | `Seance::devoirs()` | `ProgressionResource`, `SessionProgressService` |

- **Nature : complémentarité devenant doublon.** Deux représentations parallèles du même concept (« devoir donné »), sur deux tables distinctes, écrites par deux services différents du même flux (saisie de séance/progression).
- Pas un simple legacy : les deux sont vivants. Pas de suppression ici.
- **Décision : MODIFY** — à clarifier/unifier pendant la refonte (P1), en choisissant une seule source de vérité.

## DecisionConseil vs DecisionPedagogique

| | `DecisionConseil` | `DecisionPedagogique` |
| :--- | :--- | :--- |
| Table | `decisions_conseil` | `decisions_pedagogiques` |
| Colonnes | `conseil_classe_id`, `eleve_id`, `decision` | `eleve_id`, `classe_id`, `annee_scolaire_id`, `decision`, `motif`, `valide_par`, `valide_le` |
| Référencée par | uniquement `ConseilClasse::decisions()` (relation morte) | `BulletinService` (`enregistrerDecisionConseil`, `getDecisionConseil`), `DecisionPedagogiqueResource`, test `ResultatBulletinDecisionTest` |

- Différence réelle : `DecisionConseil` = décision par élève **liée à un conseil** ; `DecisionPedagogique` = décision validée **par classe/année avec workflow de validation**.
- En pratique, le service métier écrit dans `DecisionPedagogique` **même pour l'appel « enregistrerDecisionConseil »** → `DecisionConseil` est aujourd'hui **legacy quasi-inutilisé**.
- **Décisions : `DecisionPedagogique` = KEEP ; `DecisionConseil` = DEPRECATE** (conserver temporairement, ne pas fusionner automatiquement).
