## 2. Identité métier d'une offre

Clé réelle extraite du code (service + migrations), en 3 couches successives :

| Couche | Migration | Clé |
| :--- | :--- | :--- |
| Création | `2026_09_02_000003` | unique `offre_pedagogique_unique` = `(matiere_id, niveau_id, filiere_id, annee_scolaire_id)` |
| Rattachement classes | `2026_09_12_000001` | + `classe_id` nullable, backfill/split des offres, unique `offre_pedagogique_classe_unique` = `(matiere_id, classe_id, annee_scolaire_id)` |
| Remplacement | `2026_09_12_000002` | `dropUnique('offre_pedagogique_unique')` |
| Service | `OffrePedagogiqueService::enregistrer()` | contrôle applicatif sur `(annee_scolaire_id, niveau_id, classe_id, matiere_id)` + contexte immuable des 4 clés + `lock(annee)` |

**Clé métier = `(annee_scolaire_id, niveau_id, classe_id, matiere_id)`**, `filiere_id` étant déduit
(`$class['filiere_id'] ?? null`) et non discriminateur.

## 3. Offre de niveau

- Représentée par **`classe_id = NULL`**, portée par `niveau_id` (offre commune à toutes les classes du niveau).
- Le service normalise : `$data['classe_id'] = $data['classe_id'] ?? null;` puis
  `where('classe_id', null)` → Laravel génère `classe_id IS NULL` → la déduplication fonctionne
  **aussi pour les offres de niveau**.
- Lecture : `effective()` préfère la classe via `orderByRaw('classe_id IS NULL')`
  (offre de classe prioritaire, sinon offre de niveau), null si `actif = false`.

## 4. Offre de classe

- Représentée par **`classe_id NOT NULL`** ; le service exige que la classe existe dans l'année,
  soit `active`, et que `(int) $class['niveau_id'] === (int) $data['niveau_id']`.
- `filiere_id` est déduit de la classe ; le contexte (année/niveau/classe/matière) devient
  **immuable** après création (« Créez une nouvelle offre »).

## 5. Matrice d'unicité (relevée AVANT modification, inchangée après : service et schéma non modifiés)

| Cas | Service protège | DB protège | Résultat |
| :--- | :---: | :---: | :--- |
| 1. même année + même niveau + même matière + **classe NULL** | **OUI** (test `where classe_id IS NULL`, dans la transaction sous `lock(année)`) | **NON** — `offre_pedagogique_classe_unique` : sous MySQL 8 / SQLite les `NULL` d'un index unique sont distincts | Risque = écriture concurrente hors service → **couvert en pratique** par le verrou annuel (`organisation_pedagogique_verrous.lockForUpdate`), pas par la DB |
| 2. même année + même classe + même matière | **OUI** | **OUI** (`offre_pedagogique_classe_unique`, `Non_unique = 0`) | Double protection |
| 3. années différentes | autorisé (année dans la clé) | autorisé (année dans la clé) | Autorisé — correct |
| 4. niveaux différents | autorisé (niveau dans la clé) | autorisé (classe différente ⇒ index distinct) | Autorisé — correct |
| 5. classes différentes | autorisé (classe dans la clé) | autorisé (index distinct) | Autorisé — correct |

## 14. Migration éventuelle

**Aucune migration créée.**

Justification (§5 et §15 du cahier des charges) :

1. L'invariant « offres de niveau » (classe NULL) **ne peut pas** être exprimé par
   `unique(annee, niveau, classe, matiere)` : sous MySQL 8 **et** SQLite, les `NULL` d'un index
   unique sont mutuellement distincts → la contrainte protégerait les offres de classe (déjà
   couvertes) et **laisserait de côté les offres de niveau**.
2. Un index **partiel** (`… WHERE classe_id IS NULL`) existe sur SQLite mais **pas sur MySQL**
   (moteur réel du projet) ; l'alternative MySQL (colonne générée/expression) exigerait du SQL
   brut dialectique, une colonne générée supplémentaire et une vérification de réplication →
   **complexité disproportionnée** face à une protection déjà assurée par le verrou annuel.
3. Contrôles préalables réalisés : moteur réel = MySQL 8.4, 14 lignes inspectées,
   **0 doublon** → la migration n'aurait de toute façon bloqué personne ; rien n'a été modifié.

```
DB CONSTRAINT: NON            (offres de niveau ; l'index de classe existe déjà)
SERVICE GUARANTEE: OUI        (transaction + lockForUpdate annuel + contrôle 4 clés)
```
