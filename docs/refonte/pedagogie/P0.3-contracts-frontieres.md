## AttendanceEngine

### Données réellement lues

1. `presences.statut` pour un élève à une date (join `seances.date_seance`) → colonne unique `presences.statut`.
2. Nombre de lignes `presences` du jour (`seances_renseignees`).
3. `seances.date_seance` + `seances.emploi_du_temps_id` + `emplois_du_temps.classe_id` → dénombre les **séances prévues sans appel** (anomalie `MISSING_ATTENDANCE_CALL`, source `pedagogie`).
4. (élément Scolarité, hors Pédagogie) `inscriptions` pour retrouver la classe de l'élève.

### Ce qu'Assiduité cherche à obtenir

Le **statut agrégé quotidien** de l'élève (`present` / `absent_presume` / `retard` / `depart_anticipe`), sa **confiance** (100 si appel renseigné, 60 si séance sans appel, 0 sinon) et la détection des **appels manquants** — pour alimenter `AssiduiteJournaliere` et `AnomalieAssiduite`.

### Contract existant suffisant : **NON (partiel)**

- `Pedagogie\Contracts\PresenceServiceInterface::getStatutJour(int $eleveId, DateTimeInterface $date): ?string` **existe** et est documenté comme « point d'entrée pour les autres modules » — mais il ne renvoie que le **dernier** statut enregistré (`latest('id')->first()`), **sans** l'agrégation multi-séances (priorité `absent` > `retard` > `depart_anticipe`) ni le décompte « séances prévues / séances renseignées ».
- Assiduité ne l'appelle pas ; elle refait tout en SQL brut.

### Contract minimal nécessaire (NE PAS CRÉER — description uniquement)

Une seule méthode de lecture, retournant des scalaires, couvrant exactement les 3 besoins :

```php
// interface de lecture Pédagogie (statut d'appel par jour)
public function getBilanAppelJour(int $eleveId, \DateTimeInterface $date): array;
// retour :
// [
//   'statut'             => 'present|absent|retard|depart_anticipe'|null,  // agrégé multi-séances
//   'seances_renseignees'=> int,
//   'seances_prevues'    => int,   // séances programmées de la classe sans appel
// ]
```

Aucune autre méthode n'est nécessaire pour `AttendanceEngine` (le reste de son entrée vient de Scolarité/Socle/RH). Alternative complémentaire possible : un Event « appel enregistré » (voir section suivante) pour le recalcul temps réel, mais `calculer()/recalculer()` est un modèle **pull** → le contrat de lecture est indispensable.

## Frontière Presence / Assiduité

- **Owner observation séance (Pédagogie)** : `seance_id`, `eleve_id`, `statut` (appel), `saisi_par`, verrouillage `Seance.appel_verrouille`, écriture via `PresenceService::faireAppel()` / `enregistrerPointage()`.
- **Owner suivi institutionnel (Assiduité)** : `heure_arrivee` (retard), `justifie`, `document_justificatif_id`, `motif`, historique, anomalies — `PresenceService::justifierAbsence()` y touche déjà (dépôt de justificatif via GED Socle).
- **Données devant traverser la frontière** : le bilan d'appel quotidien (statut agrégé, séances renseignées/prévues) vers Assiduité ; éventuellement un signal « appel renseigné / séance dispensée » pour déclencher un recalcul.

### Mécanisme cible : **LES DEUX (CONTRACT + EVENT)**

Justification à partir des usages existants :
- **CONTRACT** : `AttendanceEngine` recalcule à la demande (`calculer`, `recalculer`) → mode pull → exige une méthode de lecture (cf. contrat minimal ci-dessus). Le pattern « Contract de lecture documenté pour les autres modules » existe déjà dans `PresenceServiceInterface::getStatutJour()` et `SeanceServiceInterface::getStatut()/marquerProgressionRenseignee()` (ce dernier documente explicitement « mettre à jour le flag côté Assiduité sans y accéder directement »).
- **EVENT** : le pattern d'Event cross-module **existe et fonctionne** (`ReportCardPublished` avec `ShouldDispatchAfterCommit`, écouté par Communication) → réutilisable pour « AppelEnregistre » (après commit) afin que P0.3 ne réinvente rien.
- Un seul des deux suffirait partiellement : le contrat couvre le recalcul à la demande, l'event couvre l'instantanéité. D'où combinaison.

*(Aucun split effectué dans P0.3, conformément aux interdits.)*
